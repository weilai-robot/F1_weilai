问题 2 · 对应审查发现 02

「使能」是假装的

代码已改 · 待实机验证
Encos 电机没有使能命令，现有代码把使能做成空操作（本地记状态、无反馈也返回成功）。后续怎么修？

确认采用的方案（已实施 2026-11-24）：不跳过，把使能重定义为「准入门槛」

  1. 使能 = 证明在线 + 进入零力矩保持：EnableActuator 的成功条件改为「超时时间内收到该电机的有效反馈帧（证明总线通、电机在线）+ 下发零力矩 MIT 保持帧」；收不到就返回 false，上层 InitDcu 现有的 THROW 会直接停机。实施时「有效反馈帧」定义为 state_msg_->id == id_ 的逐电机反馈帧（0x7FF 广播应答除外）——该判定同时是审查发现 09①，本次一并落地。
  2. 失能 = 拒绝命令：SetMitCmd 入口增加门控——power_state_ 为 DISABLE 时不接受运动命令、不写帧，发送槽保持现状（与问题 3 修订衔接：从未激活的电机保持静默 dlc=0，使能后失能的电机保持零力矩保持帧）。
  3. 接口不变：对外 enable / disable 调用形式不变；对 Encos 的语义由「固件使能位」变为「主站准入控制」。
encos_motor.cpp · RequestState/GetPowerState/SetMitCmd/UpdateFeedbackencos_motor.cpp · WriteMitCmd（无门控内部写入）encos_slave.cpp · EnableActuator（结构不变）
结论：代码已实施 · 待实机验证

实现要点：RequestState(ENABLE) 只写零力矩保持 + 置 pending，不再本地置位；UpdateFeedback 收到有效帧（id == id_）且 pending 时直接升 ENABLE（经用户确认的简化：不设独立证据变量，裁决随解析发生，GetPowerState 退化为纯 getter；当前启动时序下与轮询裁决零行为差异）；SetMitCmd 在 DISABLE 态拒绝运动命令（RequestState 经 WriteMitCmd 内部写入绕过门控，避免自锁）。待验证：使能超时→停机路径、失能后命令被拒、正常使能时延≈反馈到达。已知边界：SetEffort/SetVelocity/SetPosition 三条运动命令路径暂未门控（当前控制器不调用）。

问题 3 · 对应审查发现 01

上电就发错误命令（P0）

代码已改 · 待实机验证
「上电发错命令」是什么意思？注册时发全 0，怎么修？是不是换成全 0 力矩的帧？

确认采用的方案（2026-11-24 修订）：注册后不发帧（dlc=0 静默），使能时才激活槽位

  • 问题成因：注册电机时（SetDataFiled）往发送槽写的是 data 全 0 的帧（id/dlc=8 预武装）；总线一进 OP 就开始每 1ms 循环外发。MIT 帧是无符号码值，全 0 字节 ≠ 零力矩——0 码值解码为量程最小值（A8116 即 −130 N·m），电机持续收到大负力矩命令。enable_actuator=false 时这个错误帧会永远发下去。
  • 修法：SetDataFiled 只绑定指针并保持 memset 全零（dlc=0），删除 id/dlc=8 预置——板端按 R-601 全 6 槽扫描、dlc==0 空槽跳过（4fb775b 对齐 demo 板），注册到第一次写帧前总线完全无该电机帧。第一次有意写帧来自使能路径：RequestState(ENABLE) → SetMitCmd 零力矩保持帧（kp=0 / kd=0 / toq=0），从下一拍起 1kHz 重放；失能路径同样写零力矩保持帧。所有写帧路径（SetMitCmd / WriteCurTorCmd / SetHomingPosition）均自行重写 id/rtr/dlc，不依赖注册预置。
  • 备选方案（降级保留）：原「注册时预置中点码值零力矩帧」（12 位力矩场 ≈ 2047/4095，位置场 0x7FFF）——若需要 enable_actuator=false 时被动监测腿关节反馈（静默则反馈槽无数据，joint_state 发布全零），或规范要求「注册即受控空力矩」，回退此方案。
  • 待验证：实机确认 dlc=0 槽不产生 CAN 帧（示波器 / CAN 盒，R-601 对齐验证）；代码在 Linux 目标环境编译。
encos_motor.cpp:39-55 · SetDataFiledencos_motor.cpp · RequestState/SetMitCmd 零力矩保持encos_slave_fw_impl_spec.zh_CN.md · R-601
结论：方案修订已确认（2026-11-24）

主修改为「不发帧（dlc=0）静默」：安全不依赖预置编码正确性，实现为删代码，与问题 2「准入门槛」（使能=第一次有意写帧）同一不变量。

问题 5 · 对应审查发现 09

反馈数据「装新鲜」

Encos 侧方案已明确 · 架构级待讨论
Encos 新代码叠加的问题该怎么解决？

新鲜度问题的通俗解释

  • 正常时：电机每毫秒回一帧状态，控制器拿最新帧算下一步。
  • 反馈断了之后：软件收不到新帧，但不清掉旧数据，继续沿用最后一次的值，并且每毫秒盖一个「当前时间」戳——下游看时间戳是新的，以为数据实时。
  • 归属：重打时间戳、无超时这套机制是原 x1-infer 就有的，上肢（DCU）与下肢（Encos）都受影响；Encos 新代码又叠加两个特有问题——dlc=0 时保留旧缓存（encos_motor.cpp:71）、除 0x7FF 外不校验帧 ID 是否属于本电机（encos_motor.cpp:74-88）。DCU 槽位按位置切分不会串台，Encos 槽内是带 CAN ID 的帧，有串台风险，所以下肢风险面更大。

Encos 侧修复方案（通信层职责内，已明确）

  1. UpdateFeedback 校验 state_msg_->id == id_，非本电机的帧不解析。
结论：新鲜度问题暂缓实施（2026-11-24）

① Encos 侧数据年龄 / 运行期超时处置（发现 09②③）暂不实施，维持现状——含 x1-infer 原有的重打时间戳机制；② 09① id 校验已随问题 2 落地（commit 9f632f4）；③ 架构级时间戳 / 超时机制后续再议。方案要点（含陈旧检测难点与板卡计数器 / 主站启发式两案）已存档 OpenViking 笔记，重启时直接取用。

问题 6 · 对应审查发现 12

实时调度静默失效

分支已修复 · 待合并验证
是原有 x1-infer 的问题，目前代码能正常跑，是否修改还需再确认。

已确认的事实（代码位置）

  • 判错 bug：comm_utils.cpp:53 用 < 0 判断 pthread_setschedparam 失败——pthread 失败返回正数错误码，永远不会小于 0，所以设置失败也会打出成功日志。
  • 调用点：ethercat_manager.cpp:341（EtherCAT 周期线程），参数来自 dcu_x1.yaml:82-83（优先级 90 / 绑核 9）。
  • 权限不足：run.sh:11 只给了 cap_net_raw=ep；SCHED_FIFO 需要 CAP_SYS_NICE，实际返回 EPERM，再被上面的判错 bug 吞掉。
  • 未配置的线程：发布线程（dcu_driver_module.cc:67）、命令回调、控制主循环、ONNX 推理线程都没有配实时调度。
结论：test/f1-comm-verify 分支已实现修复（2026-11-24 调研，自 Humanoid_motion 移植），合并后闭环

四项修复（对应上方四个事实）：① 判错 bug comm_utils.cpp 判据 <0→!=0（a8b3fa0）；② WorkLoop 检查 SetRealTimeThread 返回值、失败 ERROR 告警不再静默（5de58aa）；③ control_module 增 rt_priority/bind_cpu 配置（rl_x1.yaml 80 / CPU6），rl_control_pub 主循环进 SCHED_FIFO+隔离核（ea2909b）；④ ONNX 线程限制 inter/intra_op_threads（yaml 可配默认 1）+ allow_spinning=0 禁自旋（6592df5）。

门禁体系（把"启动后确认实时性"自动化）：rt_perm_check.sh 启动前 RT 资格预检（root / cap_sys_nice / rtprio 限额三判据，权限不足显式拒绝上电）；f1-rt-verify.service 开机全量验收产出 /run 凭证 + rt_gate_check.sh 网口/CPU 活体门禁；rt_verify.sh 启动后逐线程核 comm/cls/rtprio/psr（专治线程名在但 cls=TS 的假实时）；run_main.sh preflight 三路预检→拉起→验证→SIGTERM 转发（保证 Shutdown 下使能）。

遗留与合并：发布线程（PublishLoop）仍未配 RT；分支基于 344c163 分叉，与 main 互补可合并（x1_cfg.yaml 同行同改自动合并）。
